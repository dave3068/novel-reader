# 小说阅读器 UI 技术选型实施方案

> 文档状态：技术选型执行方案  
> 编制日期：2026-09-03  
> 修订日期：2026-09-05  
> 依据文档：`docs/novel-reader-solution.md`  
> 本阶段目标：通过可复现的原型和量化测试确定第一期 UI 技术栈，不实现正式产品

## 1. 选型目标

为 Android 12+、Windows 10/11 和主流 Linux LTS 选择一套适合轻量级小说阅读器的 UI 技术架构。候选既可以是三平台共享 UI，也可以是“平台原生 UI + Rust 共享阅读业务库”的组合架构。

最终选择必须同时满足：

1. 支持三个目标平台。
2. 能够正确排版和渲染以中文为主的小说文本。
3. 能够可靠计算一页实际容纳的文本范围。
4. 能够与 Rust 阅读核心低成本集成。
5. 发布包体、内存、CPU、GPU 和功耗符合轻量化目标。
6. 静止阅读时不会保持无意义的持续刷新。
7. 支持触摸手势、鼠标、键盘、文件选择和基础无障碍。
8. 许可证满足项目开源、免费发布的要求。
9. 工程具备可构建、可测试、可持续维护的条件。

本阶段不以开发速度或界面动画效果作为第一优先级。资源占用、中文分页能力和长期可维护性优先。

## 2. 选型原则

### 2.1 先设淘汰条件，再进行评分

某项技术如果无法满足关键能力，即使其他指标得分较高也不能入选。通过所有硬性门槛后，再进行加权评分。

### 2.2 使用相同原型和测试数据

所有候选技术必须实现相同界面、调用相同 Rust 测试核心、使用相同数据集和测试设备。不得使用简单 Hello World 的结果代替真实阅读场景。

### 2.3 只测试 Release 构建

包体、启动、内存、CPU、GPU 和功耗只以 Release 构建为准。Debug 构建仅用于开发和故障定位。

### 2.4 测试可复现

每次结果必须记录：

- UI 框架和编译工具版本；
- 依赖锁定文件；
- 构建命令；
- 构建参数；
- 操作系统及设备信息；
- 测试数据版本；
- 原始测量结果；
- 中位数、P95 和异常值说明。

### 2.5 不预设 GPU 或软件渲染结论

GPU 渲染不一定更耗电，软件渲染也不一定更省电。是否适合阅读器，应根据静止状态是否停止出帧、翻页成本和物理设备功耗确定。

## 3. 候选方案

### 3.1 候选 A（优先验证）：桌面 Rust + Slint、Android 原生 UI、Rust 共享阅读业务库

架构：

```text
Windows / Linux                      Android
Slint UI                            Kotlin + Jetpack Compose
   │                                （必要时使用原生 View/Text API）
   │                                   │
Rust 桌面应用层                      JNI / 稳定 C ABI 适配层
   │                                   │
   └────────── Rust 共享阅读业务库 ─────┘
```

Rust 共享阅读业务库负责：

- TXT/ZIP 等内容访问、编码处理和有限窗口读取；
- 书籍、分类、章节、历史、书签和阅读设置等领域模型；
- 阅读位置、分页锚点、页面缓存策略和重排失效规则；
- 搜索、任务取消、错误模型及异步事件；
- 与具体 UI 排版实现无关的业务状态机和可复用测试。

桌面端直接使用 Rust API，并由 Slint 完成界面和文字测量。Android 端使用 Kotlin 原生界面，通过薄 JNI/C ABI 适配层调用同一 Rust 业务库；系统文件选择、返回手势、生命周期、无障碍和文字排版优先采用 Android 平台能力。

重点：

- Rust 业务库能否形成稳定、UI 无关的共享边界，避免在 Kotlin 中复制阅读业务；
- 桌面 Slint 的中文字体回退、分页位置查询和静止功耗；
- Android 原生文字布局能否准确返回页末位置，并与 Rust UTF-8 字节偏移互相映射；
- Android JNI/FFI 的字符串复制、线程切换、取消、异常和生命周期；
- 两套 UI 的分页结果允许因字体与平台排版不同而不同，但必须满足相同的内容连续性和位置语义；
- 跨平台功能一致性、重复 UI 代码量、自动化测试覆盖和长期维护成本；
- Windows/Linux 发布体积，以及 Android 原生包体、启动、内存和功耗；
- Slint 与 Android 依赖的许可证和发布义务。

该方案是后续技术验证的**首要方案**。验证时应优先投入设备、原型和问题排查资源，先完成其桌面与 Android 分页闭环，再开展其他候选的完整原型。UI 代码不完全共享本身不是淘汰理由；应重点判断原生平台适配收益是否大于双 UI 的维护成本，以及 Rust 阅读业务库是否真正实现了核心业务复用。

### 3.2 候选 B：三平台 Rust + Slint

架构：

```text
Slint UI
   │
   └── Rust 应用服务及阅读核心
```

需要验证的变体：

- Slint + Winit + FemtoVG；
- Slint + Winit + Skia；
- Slint 软件渲染器仅作为验证项，不默认视为可用方案。

重点：

- 与 Rust 的直接集成成本；
- 中文字体回退和复杂文字渲染；
- 是否有稳定公共接口获得分页所需的行和字符边界；
- Android 文件选择、系统栏、返回手势和生命周期；
- FemtoVG 与 Skia 在包体、中文质量及功耗上的差异；
- Linux Wayland/X11 的行为；
- 项目许可证和 Slint 许可义务。

已知必须专项验证的问题：Slint 官方资料明确指出软件渲染器的文本渲染目前主要限于西文，因此不得因其轻量而直接采用；中文版本必须验证其他渲染器，或者证明可通过可靠方案补足。

### 3.3 候选 C：Flutter + Rust FFI

架构：

```text
Flutter UI / Dart
   │
   └── C ABI / dart:ffi
          │
          └── Rust 阅读核心
```

重点：

- Android、Windows、Linux 发布包体；
- Flutter 引擎和 Dart 运行时的基础内存；
- 静止阅读是否持续调度帧；
- `TextPainter`/`Paragraph` 是否能稳定返回页面末尾位置；
- Rust FFI 的字符串复制、线程回调和生命周期成本；
- 桌面文件选择及 Linux 发行包依赖；
- Android 分 ABI 发布后的实际包体。

Flutter 具有行度量、位置查询和段落布局接口，因此分页可行性应重点通过原型验证，而不能只验证普通 `Text` 控件显示。

### 3.4 候选 D：Compose Multiplatform + Rust FFI

架构：

```text
Compose Multiplatform UI / Kotlin
   │
   ├── Android：Jetpack Compose
   └── Desktop：JVM + Skia
          │
          └── JNI/JNA 或稳定 C ABI
                 │
                 └── Rust 阅读核心
```

重点：

- Android 与桌面共享 UI 的实际比例；
- `TextMeasurer` 和 `TextLayoutResult` 的分页能力；
- JNI/JNA 与 Rust 之间的数据复制和线程切换；
- 桌面 JVM、Skia 和裁剪后运行时的发布体积；
- JVM 基础内存、启动速度和空闲 CPU；
- Windows/Linux 安装包制作；
- 平台专属文件选择和生命周期代码量。

桌面端需要将 JVM 运行时纳入完整发布包计算，不能只统计应用 JAR。

### 3.5 候选 E：Qt Quick/QML + Rust C ABI

架构：

```text
Qt Quick / QML / C++
   │
   └── C ABI
          │
          └── Rust 阅读核心
```

重点：

- `QTextLayout` 的分页、Unicode 行边界和字形能力；
- Qt Quick 静止场景的渲染和线程行为；
- QML、Qt 库、插件及字体依赖的最终发布体积；
- Android 包体和启动速度；
- Windows/Linux 完整部署；
- C++ 桥接层的复杂度和安全边界；
- LGPL/GPL 模块选择、动态链接及发布义务。

Qt 的评估必须基于完整可运行发布目录，不得只统计业务可执行文件。

### 3.6 暂不进入首轮验证的方案

以下方案暂不进入完整原型：

- Electron；
- 通用 WebView/Tauri 路线；
- Avalonia/.NET。

原因是第一轮将优先验证“桌面 Rust + Slint、Android 原生 UI、Rust 共享阅读业务库”。其他进入首轮的候选用于提供共享 UI 路线的对照基线；上述暂缓方案在主要候选均未通过硬性门槛时再评估。

## 4. 首轮硬性门槛

任何候选出现以下任一情况即淘汰：

1. 无法在 Android 12、Windows 10/11 或目标 Linux LTS 正常构建运行。
2. 中文正文出现不可接受的缺字、乱码、标点位置错误或字体回退失败。
3. 无法通过稳定公共 API 获得一页结束位置，只能依赖截图识别、私有 API或不可维护的补丁。
4. 连续翻页出现稳定可复现的丢字、重字、拆分 Unicode 字符或页面死循环。
5. 无法与 Rust 核心进行双向调用，必须在 UI 层复制整本正文，或无法把主要阅读业务稳定复用到三个目标平台。
6. 静止阅读时存在无法关闭的持续动画、持续出帧或异常后台计算。
7. 无法使用系统文件选择器，或 Android 无法持久保存文档访问权限。
8. 基础触摸、鼠标、键盘或返回操作存在无法规避的严重问题。
9. 发布许可与计划采用的项目开源许可证无法兼容。
10. 仅能通过打包大量非必要运行时、服务或浏览器环境才能工作，且资源表现明显偏离项目目标。

## 5. 原型边界

每个候选原型只实现技术选型所需的最小闭环，不接入正式数据库和完整阅读引擎。

### 5.1 共同页面

#### 书架页

- 6 层树形分类；
- 10,000 本模拟书籍；
- 当前分类书籍虚拟化列表；
- 按书名和文件名即时搜索；
- 最近阅读区域；
- 切换至阅读页和配置页。

#### 阅读页

- 当前页、上一页、下一页三页缓存；
- 简体中文正文；
- 整页翻页；
- 左、中、右点击区域；
- 左右滑动手势；
- 按钮操作模式；
- 中部点击呼出或隐藏菜单；
- 页码输入框；
- 章节列表弹层；
- 书签按钮；
- 横竖屏或窗口大小变化后的重新分页；
- 明亮、暗黑和背景图片三种显示场景。

#### 配置页

- 字体选择；
- 字号、行距、段距、边距调整；
- 文字颜色和背景颜色；
- 背景图片开关；
- 手势/按钮模式切换；
- 返回阅读页后立即重新排版。

### 5.2 不实现内容

- SQLite；
- 完整章节扫描算法；
- 正式 ZIP 解压；
- 真实阅读历史持久化；
- 正式书签数据库；
- EPUB 等格式；
- 连续滚动；
- 网络功能。

## 6. 固定 Rust 共享阅读业务库原型

为了比较 UI 与 Rust 集成成本，所有候选应调用同一个最小 Rust 动态库或静态库。

建议目录：

```text
experiments/ui-selection/
├── shared/
│   ├── rust-reading-core/
│   ├── fixtures/
│   └── ffi/
├── hybrid-native-probe/
│   ├── desktop-slint/
│   └── android-native/
├── slint-probe/
├── flutter-probe/
├── compose-probe/
├── qt-probe/
├── scripts/
├── results/
└── report/
```

本方案仅定义上述目录，执行技术验证时再创建。

### 6.1 Rust 共享阅读业务库职责

- 打开 100MB 和 1GB 测试 TXT；
- 按字节偏移读取有限窗口；
- 对 UTF-8 内容返回当前窗口；
- 生成模拟分类、书籍、章节和历史数据；
- 管理当前内容位置、分页锚点、书签和阅读设置；
- 提供页面边界登记、查询及排版配置变更后的缓存失效接口；
- 提供异步事件回调；
- 记录每次 FFI 调用耗时和复制字节数。

Rust 共享库不负责最终字形布局；各平台 UI 必须完成文字测量，并把页面结束位置映射回内容偏移。共享库应统一内容窗口、位置语义、分页锚点和缓存策略，使桌面与 Android 只保留平台相关的排版和交互代码。

### 6.2 固定边界接口

建议使用稳定 C ABI 作为共同基线：

```c
nr_engine_create()
nr_engine_destroy()
nr_open_book()
nr_read_window()
nr_release_buffer()
nr_get_book_batch()
nr_get_chapter_batch()
nr_save_position()
nr_commit_page_boundary()
nr_invalidate_layout()
nr_subscribe_events()
nr_cancel_request()
```

数据传递要求：

- 字符串统一为 UTF-8 指针加长度；
- 不使用以 `\0` 结尾作为唯一长度依据；
- 明确内存由哪一侧申请和释放；
- 不跨边界传递语言专属对象；
- 正文按窗口传输，不传递整本文件；
- 异步回调必须切换到 UI 框架允许的线程；
- 每个候选实现相同的取消和错误处理。

Slint 可以额外记录直接调用 Rust API 的优化结果。优先候选的桌面端以直接 Rust API 为正式架构，Android 端保留薄 JNI/C ABI 适配；性能对比时仍需记录等价请求的数据量、复制次数和耗时，避免因调用形式不同造成比较失真。

## 7. 分页能力专项验证

分页是本项目 UI 选型的关键，不应放到正式开发阶段再验证。

### 7.1 `PageLayouter` 原型接口

每个候选必须实现等价接口：

```text
layout_page(
    utf8_text_window,
    width,
    height,
    font,
    font_size,
    line_spacing,
    paragraph_spacing,
    first_line_indent
) -> {
    consumed_utf8_bytes,
    visible_line_count,
    last_line_metrics,
    layout_time
}
```

返回的 `consumed_utf8_bytes` 必须位于合法 UTF-8 字符边界，并能映射至 Rust 核心的原始内容位置。

### 7.2 正向分页

从起点连续翻 1,000 页，验证：

- 页面之间没有丢字；
- 页面之间没有重字；
- 不拆分 Unicode 标量或扩展字符序列；
- 空行、CRLF、LF 和长段落行为稳定；
- 相同配置下重复分页结果一致；
- 每页结束位置严格向前推进。

### 7.3 反向分页

从任意页面返回上一页，验证：

- 返回结果与此前正向分页的上一页一致；
- 不依赖把全部已读页面永久保存在内存；
- 使用稀疏锚点后能在有限读取窗口内恢复上一页。

首轮原型允许使用已记录页边界验证反向跳转；同时记录以后实现无缓存反向定位所需的接口能力。

### 7.4 重新排版

分别改变：

- 窗口宽度和高度；
- 屏幕方向；
- 字体；
- 字号；
- 行距；
- 段距；
- 页边距。

验证重新排版后：

- 当前阅读位置仍锚定在原文字附近；
- 总页数变化不影响内容位置；
- 没有旧页面闪烁；
- 页面末行不会被裁掉；
- 排版不会在 UI 线程产生长时间阻塞。

### 7.5 中文测试字符

固定测试集至少包含：

- 简体中文和繁体中文；
- 全角中文标点；
- 引号、书名号、省略号、破折号；
- 中文、英文和数字混排；
- 生僻字及字体缺字；
- Emoji 和代理对字符；
- 组合字符；
- 超长无空格行；
- 大量空行；
- CRLF、LF 和混合换行；
- 章节标题及首行缩进。

## 9. 测试设备

### 9.1 Android

至少两台物理设备：

1. 基准低配设备：Android 12、4GB 内存、60Hz 屏幕、中低端 ARM64 芯片。
2. 代表性设备：当前仍常用的 Android 版本、8GB 或以上内存、高分辨率屏幕。

模拟器只用于功能调试，不用于内存、GPU 和功耗结论。

### 9.2 Windows

- Windows 10 或 11；
- 8GB 内存；
- 集成显卡；
- 固态硬盘；
- 1920×1080、100% 和高 DPI 两种缩放条件。

### 9.3 Linux

- 选择项目计划支持的最低 glibc 基线；
- 至少测试一个 Ubuntu LTS；
- 集成显卡；
- Wayland 和 X11 各验证一次；
- 记录桌面环境、显示缩放和字体配置。

所有候选必须在相同设备上比较。

## 10. 构建规范

### 10.1 通用要求

- 锁定确切版本，不使用浮动依赖；
- 开启 Release 优化；
- 移除调试符号，另行保存符号文件；
- 禁止加入分析、崩溃上报和网络 SDK；
- 不加入原型不需要的组件；
- 默认不捆绑完整 CJK 字体；
- 使用系统中文字体进行包体测试；
- 另安装一套相同测试字体用于跨平台排版对照；
- 保存完整构建日志和依赖清单。

### 10.2 发布物统计口径

必须统计用户实际获得并能够独立运行的完整发布物：

- Android：按 ARM64 单 ABI 的 Release APK，以及安装后的实际占用；
- Windows：完整便携目录压缩包和安装包；
- Linux：选定发布格式的完整包，以及必要运行依赖说明。

不得使用以下口径：

- 仅统计主可执行文件；
- 排除必须随程序分发的运行时；
- 假设用户已预装项目依赖但正式方案并不保证；
- 将调试包与其他候选的发布包比较。

## 11. 测量场景

每项测试至少预热 1 次、正式执行 10 次；启动和交互记录中位数及 P95。功耗测试至少执行 3 轮。

### 11.1 包体

记录：

- 原始发布包大小；
- 解压后大小；
- Android 安装后占用；
- 各主要库或模块占比；
- 启用代码裁剪前后差异；
- 不同 CPU 架构拆分结果。

### 11.2 冷启动

场景：

1. 进程完全停止；
2. 清理系统近期任务影响；
3. 启动至书架首屏可交互；
4. 启动至恢复上次阅读页可交互。

记录：

- 进程启动耗时；
- 首帧耗时；
- 首次可交互耗时；
- 峰值 CPU；
- 启动峰值内存。

Android 以 `adb shell am start -W` 为基础，并结合 Perfetto/系统跟踪确认首帧和线程活动。

### 11.3 空闲内存

分别在以下页面停留 60 秒后记录：

- 空书架；
- 10,000 本书的书架；
- 纯色背景阅读页；
- 背景图片阅读页；
- 配置页。

记录：

- Android PSS/RSS；
- Windows Working Set、Private Bytes；
- Linux RSS/PSS；
- 60 秒内存增长量；
- 触发 GC 或框架缓存后的稳定值。

### 11.4 静止 CPU/GPU

阅读页停止操作 5 分钟：

- 禁止动画；
- 屏幕常亮；
- 固定亮度；
- 不运行后台索引；
- 分别测试纯色和背景图片。

记录：

- 平均及峰值 CPU；
- UI、渲染线程唤醒情况；
- 实际产生的帧数量；
- GPU 活跃时间；
- 是否存在固定周期定时器；
- 温度变化。

Android 使用 Perfetto、`dumpsys gfxinfo`、`dumpsys meminfo` 和系统进程统计交叉验证。桌面端使用操作系统性能工具，并保存原始跟踪文件。

### 11.5 翻页

执行：

- 连续前翻 200 页；
- 连续后翻 100 页；
- 10 次章节跳转；
- 10 次页码跳转；
- 20 次显示/隐藏菜单；
- 5 次字号切换；
- 5 次窗口尺寸或横竖屏切换。

记录：

- 输入到内容更新的延迟；
- P50、P95 和最大帧耗时；
- 丢帧和卡顿数量；
- 页面布局耗时；
- FFI 调用耗时及复制字节数；
- 峰值内存；
- 操作结束后的内存回落。

### 11.6 书架压力

对 10,000 本书执行：

- 首次进入书架；
- 滚动 60 秒；
- 搜索普通关键词；
- 搜索无结果关键词；
- 展开和折叠六层分类；
- 在分类之间切换。

验证列表虚拟化、搜索响应和内存稳定性。

### 11.7 功耗

Android 物理设备统一：

- 飞行模式；
- 关闭自动亮度；
- 固定相同亮度；
- 相同电量区间；
- 相同屏幕刷新率；
- 相同环境温度；
- 测试前等待设备降温；
- 关闭其他前台和后台应用。

场景：

1. 纯色背景静止阅读 30 分钟；
2. 背景图片静止阅读 30 分钟；
3. 固定节奏自动翻页 30 分钟。

优先使用可获得的硬件功耗仪；没有硬件仪器时，使用 Android 系统电量统计和 Perfetto 进行相对比较，并明确标注结果只适用于候选间对照。

## 13. 评分方法

通过硬性门槛的候选按 100 分评分：

| 类别 | 权重 | 内容 |
|---|---:|---|
| 资源效率 | 35 | 包体、空闲内存、峰值内存、CPU、GPU、功耗、启动 |
| 中文阅读与分页 | 20 | 中文质量、分页正确性、字体、重排、背景 |
| 跨平台完成度 | 15 | 三平台功能一致性、文件选择、输入、高 DPI、系统集成；不以 UI 源码共享率直接计分 |
| Rust 集成 | 15 | 阅读业务复用范围、FFI 成本、数据复制、线程、错误处理、构建复杂度 |
| 工程与维护 | 10 | 工具链、调试、测试、升级风险、社区和文档 |
| 无障碍与用户体验 | 5 | 语义、键盘导航、触摸目标、系统返回行为 |

### 13.1 量化指标换算

包体、内存、CPU、功耗和启动时间使用候选实测值归一化。最低资源消耗得满分，最高资源消耗按比例扣分。

不得因为某个框架“理论上更轻”给予分数，必须提供实测数据。

### 13.2 主观项目锚点

对不能完全量化的项目使用五级评分：

- 5：原生支持、公共稳定 API、无额外补丁；
- 4：少量平台适配即可稳定实现；
- 3：可实现，但需要明显桥接或自定义组件；
- 2：依赖脆弱方案、较多平台分支或维护成本高；
- 1：仅能勉强演示，存在重大风险；
- 0：无法实现。

每个主观得分必须附原型代码位置和问题记录。

对于双 UI 候选，必须额外记录 UI 重复代码量、平台适配代码量和共享 Rust 业务覆盖率。这些数据用于评估维护成本，但不得把“没有共享 UI”直接等同于低分；应按三平台总体实现、测试和升级成本评分。

## 14. 决策规则

1. 先淘汰未通过硬性门槛的候选。
2. 总分低于 75 分的候选不建议进入正式项目。
3. “资源效率”得分不得低于该类别满分的 70%。
4. “中文阅读与分页”不得低于 16/20。
5. “Rust 集成”不得低于 11/15。
6. 若最高两个候选总分相差不超过 5 分，优先选择：
   1. 静止功耗更低者；
   2. 空闲内存更低者；
   3. 完整发布包更小者；
   4. 分页接口更稳定者；
   5. 平台专属代码更少者。
7. 最终决定必须记录为架构决策文档，不以口头印象决定。

## 15. 执行阶段

### 阶段 0：冻结环境

1. 确定测试设备。
2. 确定目标 Linux 基线。
3. 记录并锁定候选框架稳定版本。
4. 确定项目拟采用的开源许可证候选。
5. 建立测试数据生成脚本和结果格式。

完成条件：

- 所有设备和版本记录完成；
- 测试数据可重复生成；
- 指标采集方法在各平台至少试运行一次。

### 阶段 1：建立共同 Rust 共享阅读业务库原型

1. 实现 UI 无关的 Rust 阅读业务 API。
2. 为跨语言候选实现最小 C ABI，并为 Android 提供薄 JNI 适配。
3. 实现模拟书架数据。
4. 实现 TXT 有限窗口读取。
5. 实现位置、分页锚点、缓存失效和异步回调。
6. 实现 FFI 调用计时。
7. 编写 Rust API、C ABI 和业务契约测试。

完成条件：

- Android、Windows、Linux 均能加载；
- 100MB、1GB 文件不会整体进入内存；
- 内存归属和释放经过测试。

### 阶段 2A：优先候选分页与共享边界尖峰

先只验证“桌面 Rust + Slint、Android 原生 UI、Rust 共享阅读业务库”：

1. 桌面 Slint 和 Android 原生 UI 分别显示一页中文；
2. 两端都能返回准确页末位置并映射为 Rust UTF-8 字节偏移；
3. 两端都能连续前翻、后翻，并在修改字号或宽度后重新分页；
4. Rust 共享库统一管理内容窗口、阅读位置、分页锚点和缓存失效；
5. Android 完成 JNI/FFI 线程、取消、异常、生命周期和 SAF 最小闭环；
6. 记录 Rust 业务复用范围及 Kotlin、Slint 平台专属代码量。

完成条件：

- 优先候选在桌面和 Android 均通过分页硬门槛；
- Android UI 层未复制文件读取、章节、位置、书签等阅读业务；
- 已识别双 UI 的主要重复代码和自动化测试策略；
- 形成继续完整原型或提前淘汰的书面结论。

### 阶段 2B：其他候选分页可行性尖峰

完成阶段 2A 后，其他候选在实现完整三页面之前先只完成：

1. 显示一页中文；
2. 返回准确的页末位置；
3. 连续前翻和后翻；
4. 修改字号和宽度后重新分页；
5. 接入 Rust 内容窗口。

任何候选未通过分页硬门槛，不再继续实现完整原型。

### 阶段 3：候选完整原型

优先完整实现通过阶段 2A 的候选，再对通过阶段 2B 且有必要保留的对照候选实现统一的：

- 书架；
- 阅读页；
- 配置页；
- 文件选择；
- Rust 调用；
- Release 发布物。

界面布局、颜色、数据和交互尽量一致。优先候选允许遵循 Android 与桌面各自的平台交互惯例，但功能语义、测试数据和 Rust 业务行为必须一致。

### 阶段 4：功能和兼容性测试

- 执行功能验收矩阵；
- 执行中文和 Unicode 测试；
- 执行 Android 生命周期、返回和 SAF；
- 执行 Windows/Linux 文件选择；
- 执行高 DPI、Wayland、X11；
- 执行许可证及依赖清单审查。

### 阶段 5：性能测试

- 构建包体；
- 冷启动；
- 内存；
- 静止 CPU/GPU；
- 翻页和重排；
- 书架压力；
- Android 功耗。

所有原始数据写入统一结果目录，不先筛选“好看”的测试轮次。

### 阶段 6：评分与决策

1. 汇总硬性门槛。
2. 淘汰不合格候选。
3. 完成量化归一化。
4. 完成主观评分及证据链接。
5. 进行一次结果复测。
6. 编写最终选型报告和架构决策记录。

## 17. 风险及控制

### 17.1 测试原型过于简单

控制：必须实现真实分页、Rust 边界、10,000 本书架和背景图片，禁止用 Hello World 结果决策。

### 17.2 不同候选实现质量不一致

控制：先定义共同交互、数据、页面结构和完成检查表；对异常差的候选允许一次针对性优化后复测。

### 17.3 字体导致结果失真

控制：包体测试使用系统字体；排版一致性测试使用各设备预先安装的同一字体；两种结果分开记录。

### 17.4 把阅读核心性能算到 UI

控制：所有候选使用相同 Rust 核心、数据和请求模式，并单独记录 Rust 耗时、FFI 耗时及 UI 布局耗时。

### 17.5 Android 功耗噪声

控制：固定亮度、刷新率、网络、温度和测试时长，至少三轮，优先使用硬件测量。

### 17.6 只关注安装包

控制：包体仅占资源效率的一部分，同时考察内存、静止 CPU/GPU、功耗、启动和分页正确性。

### 17.7 许可证在开发后期才发现问题

控制：在阶段 0 和阶段 4 分别进行一次许可证审查，记录所有框架、模块、插件、字体和第三方库的许可。

### 17.8 双 UI 导致行为分叉或维护成本失控

控制：把阅读状态机、位置语义、分页锚点、缓存规则和领域模型放入 Rust 共享库；为桌面和 Android 运行同一套业务契约测试；维护统一功能清单，并持续记录平台专属代码量和重复实现。原生交互差异允许保留，但不得演变为两套阅读业务。

## 18. 当前候选的预期关注顺序

建议按以下顺序执行分页尖峰，而不是按此顺序直接决定最终技术：

1. **桌面 Rust + Slint、Android 原生 UI、Rust 共享阅读业务库**：首要且重点验证。先确认桌面 Slint 分页、Android 原生分页、Rust 业务共享边界和双 UI 维护模型是否同时成立。
2. **三平台 Rust + Slint**：用于判断 Android 也采用 Slint 能减少多少 UI 维护成本，以及会牺牲多少原生集成与排版能力。
3. **Flutter**：作为跨平台成熟度和文字 API 的对照基线。
4. **Compose Multiplatform**：重点评估 Android 体验与桌面 JVM/Skia 资源成本。
5. **Qt Quick**：重点评估成熟文字布局能力与完整部署体积、桥接及许可成本。

阶段 2A 和阶段 3 的设备、开发及问题排查资源应优先保障首要方案。其他候选先完成足以构成客观对照的分页和资源测试，只有在首要方案出现硬性缺陷或需要进一步比较时，才扩展为同等深度的完整原型。该优先级不代表预先确定最终结论，最终仍以硬性门槛和实测数据为准。

## 19. 开始执行前需冻结的决定

以下事项不妨碍形成方案，但在实际启动原型前必须确定：

1. 项目准备采用的开源许可证候选，例如 GPLv3 或宽松许可证。
2. 最低 Linux 发行版和 glibc 基线。
3. 可用于测试的 Android、Windows、Linux 设备。
4. 是否接受为不同平台选择同一 UI 框架的不同渲染后端。
5. Android 第一发布架构是否仅 ARM64，还是同时支持 32 位 ARM。
6. 最终发布是否要求完全便携，还是允许 Linux 依赖系统基础库。
7. Android 原生 UI 以 Jetpack Compose 为默认实现时，是否允许分页组件局部使用原生 View/TextLayout API。

## 20. 官方资料核对基线

本方案编制时核对了以下官方资料；实际执行时应再次核对并锁定当时稳定版本：

- Slint：桌面及移动平台、后端与渲染器、Rust Cargo Features、Text 元素。
- Android 原生：Jetpack Compose、Android 文字布局、SAF、生命周期、返回导航、JNI 和无障碍。
- Flutter：支持平台、桌面支持、Android 发布、性能分析、`TextPainter` 和 `Paragraph`。
- Compose Multiplatform：平台兼容性、桌面原生分发、平台差异、`TextMeasurer`。
- Qt：支持平台、部署、Qt Quick 性能、`QTextLayout` 和开源许可。

官方资料只能证明框架提供相关平台或 API，不能替代本项目的实际包体、中文分页和功耗测试。

## 21. 完成标准

UI 技术选型阶段只有同时满足以下条件才算完成：

- 优先候选完成桌面 Slint、Android 原生 UI 和 Rust 共享阅读业务库的全部验证，或有明确证据证明其未通过硬性门槛；
- 至少一个对照候选完成足以支持决策的分页、Rust 集成和资源测试；
- 所有进入最终评分的候选具有三平台 Release 发布物；
- 中文正向、反向和重排分页测试通过；
- Rust 集成原型完成；
- 包体、启动、内存、CPU、GPU 和 Android 功耗数据完整；
- 功能矩阵和许可证检查完成；
- 量化评分经过一次复测；
- 输出最终选型报告；
- 输出 UI 框架架构决策记录；
- 明确首选、备选及放弃其他方案的证据。

在上述工作完成前，不应启动正式 UI 工程，也不应把任何候选框架视为已经确定。
